## 二、阶段一：合并重组（10-06）

**挫折**：能力分散在三个仓库，接线文档、固件、主机脚本各说各话，README 有三份互相矛盾的入口。

**做法**：先打一份 `baseline` 快照提交（逐字节保留重组前状态），再按用途重排目录，把三份 README 合成一份，并补 `.gitattributes` 统一行尾（Windows 脚本保持 CRLF，其余 LF）。同期把 8 个固件目录的 README 补齐、模块索引扩到 13 个。

**教训**：**先快照、再动结构**。后来两次大的方案停用（10-14、10-17）都沿用了这个模式，并且用 `manifest.json` + SHA-256 做逐字节校验（两次复核均为「缺失 0、不一致 0」）。

## 三、阶段二：麦轮底盘调不通（10-07）

**现象**：四轮麦轮底盘，串口报告一切正常（`STBY=1`、`duty=192,0,0,0`、到期自动归零），但**左前轮就是不转**。

**排查**：没有直接提占空比，而是先做对照组——
1. 同一指令在原 PR 里能转，本地不能转 → 排除「固件不会转」；
2. 换到左后轮执行同样的 `PULSE RL 192 500` → **左后轮转了**；
3. 于是把问题锁在「左前轮这一路」的物理链路上，用户随即发现**左前的杜邦线松脱**。

**根因**：接触不良，不是逻辑、不是固件、不是占空比。

**第二个挫折**：把单轮脉冲时限从 500ms 扩到 2000ms 做逐轮双向测试后，**两只后轮只有反转能起转，正转起不动**；同时 30 秒计圈显示四轮转速不一致。软件侧无法解释（四轮指令、极性、斜坡都对）。当时的处置是：不追着提占空比，改为记录「根因未定位」，并转向可量化的转速测量方法（`TT电机-转速与圈数测量方法.md`、三角波 `RAMPPULSE`）。

**教训**（后来反复用到）：
- **串口回读 ≠ 物理动作**，「软件说转了」和「轮子转了」必须分别记录；
- 先做 A/B 对照（换一路、换一轮、换一条线），再谈根因；
- 结论没证据就写成「未定位」，不要写成因。

## 五、阶段四：抛投方案第一次推翻（10-14）

**原方案**：DRV8313 + 2804 无刷电机 + AS5600 磁编码器，FOC 闭环。

**挫折 A：硬件烧坏。** 用户报告 DRV8313 已烧坏 → 方案不具备继续条件。

**挫折 B：实机抛投四项全失败**（用户现场口述，**无串口日志、无仪表读数、无照片**，文档如实标注了证据等级）：

| # | 现象 | 归类 |
| --- | --- | --- |
| 1 | 电池像是断路，只能直连电源 | 供电 |
| 2 | 3D 打印孔太大，齿轮一直滑齿，加限位器失败 | 机械加工/装配 |
| 3 | 无半月形杆，齿轮在卷线轴上滑动脱落且装不回去 | 轴与轮毂连接 |
| 4 | 人力把杆拉满，抛射初始角度仍是平的，过不了城墙 | 机构几何/设计 |

**关键判断**：第 4 项**不依赖前 3 项修好**——它是几何问题，不是零件故障。也就是说即使传动全部修好，这套机构依然打不到目标。

**处置**：当天把旧方案整体归档（126 个文件快照 + 逐字节校验），改用 L298N 驱动两台 N20 做卷线蓄力，并明确「新方案尚未编写固件或做过硬件测试」。

**教训**：**把「零件坏了」和「设计不成立」分开评估**。前者能修，后者要换方案，混在一起会导致在一个注定失败的机构上继续投入。

## 六、阶段五：卷线方案终止（10-17 上午）——本项目最严重的一次失败

**现象**：用户报告卷线/蓄力机构**扭矩过大，电机被撕裂**。

**力学根因**（工程结论，非实测）：把电机经齿轮与卷线轴**硬联**到拉绳与限位端时，机构会以堵转/冲击扭矩反作用到电机上——**力的上限由机构与限位决定，而不是由电机决定**。所以任何「硬限位 + 大减速比」的蓄力结构，都会把冲击载荷全部压到电机轴上。

**解决方案**：换成**摩擦飞轮**。能量储存在飞轮转子动能里，负载是**惯性负载**，没有硬限位反冲，力矩受电机自身的转矩—转速特性约束，从原理上避开了「电机被撕裂」这一失效模式。

**处置**：旧方案 77 个文件（70 个方案文件 + 7 个链接目标）逐字节归档，`manifest.json` 校验缺失 0、不一致 0；旧固件与主机脚本保留在原目录供追溯，但三个 N20 模块 README 标注「已停用」。

**教训**：**失效模式要按「力从哪里来」分析**，而不是只替换更结实的零件。同一时期还确立了「所有旧接线、极性、命令在归档中均为历史记录，不适用于新方案」的边界声明，避免历史资料被误当现行依据。

## 八、阶段七：整合程序与 N20 故障（10-18）

队友交付了 `ChariotIntegrated` 整合包（底盘 + 转向 + R2 飞轮 + R1 对接器），我这边先做了一次「本地 vs 远程」的合并：本地只有未提交的草稿，远程多 3 个提交，按「冲突以远程为准」做 fast-forward，本地草稿整体进 stash 备份。

随后是**本项目最曲折的一次排查**：

**挫折 A：N20 使能回读不到高电平。** R1 触发后串口显示 `feed=1` 但 `TB3=0`。定位过程：
1. 先确认不是 MCU 端问题——空载时 GPIO21 能正常拉高；
2. 发现外部有一条 **c23–d26 下拉支路**把使能拉低，取下后使能恢复；
3. GPIO22 的通路存在独立异常，**弃用 GPIO22**，STBY 改到 **GPIO21**；
4. 固件增加「使能回读失败立即停机」保护，`fault=feed_enable`。

**挫折 B：N20 在 30% 完全不动。** 这一条反复了整整一天，中间还踩了两个坑：

- **虚假结论坑**：我连续跑了 100%/150ms 和 100%/300ms 两次，都报告「不动、无声」，正准备下「排除占空比不足」的结论时，用户说「刚才没接电」——**那两轮只插了 USB，动力根本没接**。记录里当场把两轮标为作废、撤回结论。
- **二分定位**：在确认带电后逐档实测——**50% 不动、65% 只抖一下、75% 起转、80% 带负载能带动机构 3 秒**（空载门槛约在 65%~75%）。

**根因**：**启动占空比不足**。30% 时空载等效电压只有约 1.8V，连静摩擦都克服不了，电机堵转在 0 速（所以「连声音都没有」）。原版默认的 30%/150ms 是**双重不足**：电压不够，时间也太短。

**解决**：`FEED_PERCENT` 30 → 80，并把「一次脉冲」的参数交给实测决定。

**教训**（这次最贵的一课）：
- **遥测一致 ≠ 实验有效**。六轮遥测（`feed=1 TB3=1 N20pwm=...`）写得一模一样，但两轮根本没通电——**供电状态必须由人确认并在记录里单独标注**；
- 结论要能被一句话推翻（「没接电」就足以推翻），所以每条记录都要写清「当时的确切工况」；
- 提高占空比不是万能的，**先证明「能转」，再谈「转得对」**。

**挫折 C：工具链与环境。** 换到另一台机器（用户 `jiahe`）后，`arduino-cli`、`Arduino15`、MSVC 全都不在，`tests/run-integrated-tests.cmd` 里硬编码的 `C:\Users\33920\...\vcvarsall.bat` 也失效。处置：装 `arduino-cli 1.5.2`，找到 `D:\Download\arduino\data` 下的 ESP32 3.3.12 核心，主机测试改用 `g++ -std=c++17` 跑同一份测试源码。

**挫折 D：串口反复消失。** 烧录前后 COM9（CH340）两次从系统里整体消失，第二次发生在监视器读串口时（`GetOverlappedResult PermissionError`），导致一次实验数据完全丢失。处置：把监视脚本改成**断线自动重连 + 无论怎么退出都落盘**。**根因未定**——线材/接触/掉电复位都还没区分开；如果它只在 N20 起动瞬间掉线，那就和「VM 电压从未实测」是同一个供电问题。

**挫折 E：版本号漂移。** 为做带载 3 秒实验我把点动上限从 500ms 改到 3000ms，但**没升版本号**，板上二进制仍自称 `v3.3-JOG`——同名不同物，溯源只能靠哈希。发现后立即补上版本号（v3.4 起），并在文档里写明「不要用版本字符串判断二进制」。

## 九、阶段八：机构控制的定型（10-18 晚）

在确认「80% 能带载」之后，R1 的语义连续演进三版，每一版都由实测驱动：

| 版本 | 改动 | 依据 |
| --- | --- | --- |
| v3.4-R1ALT | R1 每按一次**交替方向**、80%、1750ms | 只会朝一个方向转无法做来回对接 |
| v3.5-R1LONG | 两方向时长拆开：+1 = 3000ms、−1 = 1750ms | 上升行程比下降长 |
| v3.6-HOLDUD | 新增**按住 △ = 上升、按住 × = 下降**，松手即停，上限 3000ms | 点按是定时的，机构需要「点一下走一点」的手动控制 |

期间一次误判：我以为 △ 会和底盘前进冲突（把 △ 当成了 D-pad 上键），用户纠正——**DualShock 左侧是十字键、右侧是 △○×□**，是不同的位（D-pad 4/5/6/7，△ = bit 12，× = bit 14），根本不存在冲突。核对位定义后 △ 和 × 本来就都空着。

**方向最终确认（用户现场验证）**：按住 △ = 上升、按住 × = 下降；即**上升 = 原始方向 +1（GPIO25）**，`FEED_UP_DIRECTION=1` 生效。

## 十、方法论沉淀（这套项目真正积累下来的东西）

1. **证据分级**：所有记录区分「用户口述」「串口日志」「仪表读数」「物理观察」四类，缺证据就写「未验证」，不带入下一份文档当事实。
2. **单发、限时、不重试**：每个动作指令都带硬上限（`FLY_MAX_MS`、`FEED_JOG_MAX_MS`、`FEED_HOLD_MAX_MS`），一次只发一条，防止自动重复。
3. **主机侧仿真先行**：固件源码 + 桩件在主机跑数百项检查（146 → 681 → 792 → 822 → 827 → **867** 项），能在不接硬件、不通电的情况下验证逻辑与边界。
4. **不可逆操作先快照**：两次方案停用都做了逐字节归档 + manifest 校验。
5. **遥测不能代替量测**：`STATUS` 里的 PWM 回读、STBY 电平只证明 MCU 侧，不证明电机端电压、电流或物理转动——这条被反复写进每一份记录。
6. **测前先问「现在通着电吗」**：这一条是用一次真实误判换来的。
